# 红外联机逆向笔记

本文记录 Meets / On 原版双机红外联机的协议，以及在本机模拟器里跑通
「つうしん → みーつ → あそぶ」的验证方法。目前只在 **Sweets v062** 上验证过。

## 结论

双机联机走的是红外，不是蓝牙。链路层是 IrDA 风格的自定义帧，上层是
OBEX，服务名是 `TAMA`。两台机器各自运行原版固件，由固件自己完成链路协商、
OBEX CONNECT、数据 PUT 和告别流程。

## 帧格式

一次发送由以下部分组成：

```
FF × 10        前导
C0             起始
payload        数据 + CRC
C1             结束
```

- 前导固定 10 个 `0xFF`。
- CRC 为 CRC-16/KERMIT（多项式 `0x8408`，初值 `0xFFFF`），按小端追加；
  对「数据 + CRC」整体计算，余数为 `0xF0B8`。
- `0x7D` 和 `0xC1` 出现在数据里时，写成 `0x7D` 再接 `字节 ^ 0x20`
  （即 `0xC1` 会变成 `7D E1`）。`0xC0` 不转义；它在数据中被视为重同步。
- 接收缓冲上限约 `0x40E` 字节。

### 链路请求（28 字节）

```
FF FF FF FF FF FF FF FF FF FF
C0
FF 3F 01 00 01 03 04 FF FF FF FF 00 00 00
A0 70
C1
```

其中 `A0 70` 是小端 CRC，前面的 14 字节是数据。

### 链路应答（35 字节）

对端收到请求后，会用自己的固件生成应答。实测一例：

```
FF FF FF FF FF FF FF FF FF FF
C0
FE BF 01 1C 08 24 0A 00 01 03 04 00 00 00 80 20 00 54 4D 47 43
37 17
C1
```

`54 4D 47 43` 是 ASCII 的 `TMGC`。后面的 OBEX 阶段还会出现 `TAMA`、
`TAMAGO` 等标识。

## 固件侧状态（Sweets v062）

| 地址 / 偏移 | 含义 |
|---|---|
| `[0xF8011A58]` | IR 上下文指针 `g`，本 ROM 上为 `0xF8011A5C` |
| `g + 0x00` | 接收缓冲指针 |
| `g + 0x04` | 接收缓冲大小 |
| `g + 0x0C` | 已收字节数 |
| `g + 0x18` | 接收标志（CRC 错、帧错等） |
| `g + 0x1C` | 当前字节处理函数 |
| `g + 0x2C` | 链路对象（memset 0x18 后由 `0x20191610` / `0x201916B8` 初始化） |
| `g + 0x4A8` | 应用登记的读缓冲 |
| `g + 0x4B0` | 待处理数据块 |
| `g + 0x4B4` | 链路状态：0 空闲、1 等应答、2 收到待处理 |
| `0xF8011A54/55/56` | 应用事件标志：1 / 2 / 4 |

关键函数：

| 地址 | 作用 |
|---|---|
| `0x20191324` | 把一个字节喂给当前帧处理函数 |
| `0x20190E3C` | 帧起始 / 前导处理 |
| `0x20190F54` | 帧内字节、`C0` / `C1` / `7D` 处理 |
| `0x2019106C` | 数据字节与 CRC 校验 |
| `0x20191294` | 初始化接收解析器 |
| `0x2018DA74` | 收完一帧后的回调：校验、置状态、发事件 2 |
| `0x2018DB90` | 用收到的数据块建立链路并开始发送 |
| `0x2018DC70` | 流层「收到数据」入口 |
| `0x2018DD10` | 清空接收并打开 RX |
| `0x2018D7E0` / `0x2018D824` | 置位 / 清除事件标志 |

## UART 模型

红外模块挂在 `0xC0060000`，使用 IRQ 14。

| 偏移 | 含义 |
|---|---|
| `+0x00` | 数据 |
| `+0x04` | 中断标志 |
| `+0x08` | 控制：`0x0070` 波特率位、`0x1000` 模块使能、`0x4000` 发送、`0xA000` 接收 |
| `+0x0C` / `+0x14` / `+0x1C` | 波特率分频等 |
| `+0x10` | 状态：`0x4000` 可发送、`0x0010` 接收空、`0x8000` 收到数据、`0x0080` 发送完成 |

发送完一帧后，固件会轮询状态位 `0x0080`。该位为 1 时，中断处理会：

1. 清掉 `0xE000`（关闭收发）；
2. 把链路状态置 0；
3. 调用 `0x2018DD10` 重新打开接收；
4. 置事件 4。

模拟器原先没有这个位，于是发送完就一直停在「只开发送」的状态，收不到
对端的应答。补上「发送突发结束后置 `0x0080`」之后，双机才能自行完成
收发切换。

另外，发送中断做成了每毫秒最多一次，避免电平式中断饿死游戏主循环。

## OBEX 阶段

链路建立后，固件自己发起 OBEX。实测帧里可以看到：

- CONNECT 目标头：`OBEX` + `IrDA:TinyTP:LsapSel`；
- `TAMA` / `TAMAGO` 标识；
- 一次 PUT 里带 UTF-16LE 文件名 `put1.jpg`；
- 后续大量约 500 字节的 PUT，内容是小图标 / 图案数据（`0x11`、`0x22`、
  `0x33`、`0x44` 之类的 nibble 图案）。

最后两端进入告别画面：

```
A: バイバイ★またいっしょに あそびたいっつーの
B: おでかけ ちゅう
```

## 本机验证

`rust/shell/examples/irpair.rs` 会把两个会话的 UART 对接起来：A 的发送
进入 B 的接收，B 的发送进入 A 的接收。两边都跑原版固件。

准备两个已经过首次开机的存档目录（内容可以相同），然后：

```sh
export POCKET_MEETS_ROM=/path/to/fw_tg18_jp_v062_2019-09-12_sweets.bin
cargo run --release --example irpair -- /tmp/save-a /tmp/save-b
```

要点：

- 两台机器不能完全同时开始。一个人先按、另一个人后按，先按的那台在
  发请求时，另一台还在监听。示例里让 A 先走 0.2 秒。
- 成功时最后一行是 `PASS: the two original firmwares completed an
  infrared visit`，退出码 0。
- 失败时会打印最后的画面和帧数，退出码 1。

本机实测一次完整访问约 23.5 秒、355 个红外帧，捕获到 `OBEX` 和 `TAMA`，
最后出现上面的告别文字。

### 补完的功能验证（新增）

#### アイテムこうかん

两台都到 3 才后，先买一个 `おどうぐ`：

```
メインメニュー → マイタウンで おでかけ → たまデパ → かいもの
→ アイテムショップ → キックボード (200G)
```

购买确认界面默认光标在 `いいえ`，要先按 A 移到 `はい` 再按 B。

交换路径：

```
あげる: ツーしん → みーつ → アイテムこうかん → あげる
        → もちもの → おどうぐ → キックボード
もらう: ツーしん → みーつ → アイテムこうかん → もらう
```

双方都到 `つうしん たいき…` 后，先让一方开始，0.5 秒后再让另一方开始。实测：

- A→B：109,089 字节，B 背包出现 `キックボード`，A 背包消失；
- B→A：109,092 字节，物品移回 A；
- 访问结束后照常登记 `ともだちてちょう`。

#### 照片/JPG

用 `IRCAP_DIR=/tmp/ircap irmarry ... 0 0` 抓完整 `あそぶ` 流量：

- A→B 66,717 字节，B→A 53,686 字节；
- A→B 里有 `put1.jpg` / `put2.jpg` 对象名（偏移 `0x423` 起）；
- 没有 `FF D8 FF`、`FF D9`、`JFIF`；
- 对象体是 TAMA/OBEX 数据和 UTF-16 名字，不是标准 JPEG。

所以“照片”在红外上不是以标准 JPEG 传输的；`put1.jpg` 只是对象名/缩略图容器。

- 1% 字节丢失：32,585 字节后卡在 `つうしん ちゅう`；
- 5% 字节丢失：3,031 字节后失败；

### 成长与资源

- 从婴儿档开始做 1 小时离线追赶，`ふわつのっち` 进化成 `やきマシュっち`。
- 13 小时追赶后状态页显示 `1代目 1才 300G`。
- 再做 24 小时、48 小时追赶，仍是 `やきマシュっち`，没有到成年；成年可能还需要清醒时间的照顾或更多天数。
- 婴儿档是 `0G`，儿童档是 `300G`；买食物/礼物需要先让宠物在白天清醒，或准备一个带物品的存档。



### 带 RTC alarm 的补时

只把 `care_sync` 跑起来并不会让游戏日历前进：游戏自己的日期副本（`0xBE30`）只在它“醒来/冷启动”时刷新。补时里如果 RTC alarm 没有armed，`power_cycle` 不会发生，日历就停在原处。

把 RTC alarm 设成 60 秒后并打开使能位后，补时会按分钟冷启动，日历才会翻页：

- `0x20..0x25`：alarm 计数（48 位，小端）
- `0x40`：使能，`& 6 != 0`

实测：

- 儿童 `やきマシュっち`，1 才；
- 48 小时带 alarm 的补时后变成 `めっとっち`，2 才。

对应工具：

```sh
POCKET_MEETS_ROM=... cargo run --release --example iralarm -- <save> 48
POCKET_MEETS_ROM=... cargo run --release --example irforward -- <save> 48
```

`iralarm` 回放当前 `care_at` 之前的一段，`irforward` 从 `care_at` 往后回放。两者都会写回存档，可以按不同天数切出不同年龄的存档。

目前卡在下一步：2 才的 `めっとっち` 存档启动后停在个人资料页，A 键只能打开资料/状态页，暂时回不到主菜单，所以还没法进 `みーつ → プロポーズ`。另外，继续进化可能还需要每天喂食/治病/清理，而不只是时间。


### 日常照顾与年龄存档

带 alarm 的补时里，如果一次跳 24 小时，宠物会在中途饿死/病死。按 6 小时一段、每段后喂食/治病/清理，能把它养到 3 才：

- 6 小时补时（alarm 1 小时一次）；
- `ごはん・おやつ` → `れいぞうこ` 连喂 10 口，或去 `カフェレストラン` 吃到 6/6 心；
- `きゅうきゅうばこ` 两次；
- `トイレ・おふろ` 一次；
- 存档。

实测：

- 婴儿 → `やきマシュっち`（1 才）→ `めっとっち`（2 才）→ `ござるっち`（3 才）；
- 24 小时一跳会死；6 小时一段能活；
- `あいじょー` 条不会自己涨。`たからばこ` → `ボール` / `ぬいぐるみ` → `つかう` 可以玩耍；实测 1 次约 1 格，5 次约 2 格，还需要更多玩耍/零食才能填满。
- 亲密度低时，3 才档连续 3 段（18 小时）还能活，第 4 段会死。

工具：

- `ircare3 <save> feed|med|clean|bath|play|propose`：喂食、治病、清理、洗澡、玩玩具、进入求婚菜单；
- `irsnack <save>`：去餐厅吃到饱；
- `irshot2 <save>`：把当前画面存成 `/tmp/boot.rgb`（再转 PNG 可看是不是墓碑）；
- `irhearts <save>`：打开状态页，看爱心/亲密度。

目前的 3 才存档 `/tmp/live3` 是活的，但主菜单状态停在 `おでかけ`，按 `ツーしん` 会进到出门提示，暂时打不开 `みーつ` 子菜单。婴儿档的求婚导航是通的，会显示 `まだプロポーズ できないよ！`；3 才档还需要把主菜单游标/状态复位。


### 性别条件

3 才 `ござるっち` 的个人资料页显示 **♂**，婴儿 `ふわつのっち` 也是 **♂**。两个存档都是雄性，所以：

- 菜单能进到 `プロポーズ`；
- 按 B 后没有 IR 帧（0 帧）。

说明求婚不是被亲密度挡住，而是缺少**异性对象**。后来已经孵化出雌性并养到 3 才，见下面的「雌性养成与红外求婚」。

`irgender` 可以打开个人资料页并截图，用来确认性别。

### 性别改存档的尝试

- 在宠物记录区 `0x0D7C0..0x0D870` 逐字节 XOR `0xFF`，个人资料页右下角的性别符号区域没有变化（少数偏移会让资料页打不开），所以性别不是这段里的一个简单字节/位。
- 用 `irhatch2` 连续孵了 5 个新档，个人资料页的符号区域哈希完全相同，都是 **♂**。在这个 ROM/启动条件下，蛋的性别是确定的，不是 50/50 随机。
- 因此：
  1. 改存档仍然可能，但字段不在已试的宠物记录区，可能在蛋/角色表或 flash 的初始化数据里；
  2. 更快的路是改变孵蛋时的 RTC/种子/名字，让 `rand()` 走出不同性别；
  3. 或者直接提供一个雌性存档。

`irbrute` 是这次用的逐字节扫描工具；`irhatch2` 是新鲜蛋的孵化流程。


### 角色表与资料页渲染

角色表在 ROM `0x1C5414`，每项 8 字节：名字指针 + 角色 ID。名字都在 `0x1D45xx` 一带，例如：

| ID | 名字 |
|---|---|
| 01 | ふわつのっち |
| 04 | やきマシュっち |
| 0F | めっとっち |
| 14 | ラブリっち（雌性候选） |
| 16 | ふらわっち（雌性候选） |
| 19 | ござるっち（当前 2 才档） |

资料页的渲染函数在 `0x20143CA0` 附近，会读取：

- `0xF800D840`
- `0xF800D84A`
- `0xF800D7D6`
- 结构基址 `0xF800D834` 的 `+3`（绘制索引）

把 `0xD836`、`0xD837`、`0xD83A`、`0xD84A`、`0xD7D6`、`0xDAC7` 改成雌性 ID 后，资料页名字仍然是 `ござるっち`；把 `0xD840` 改成 `0x14/0x16/0x19` 会让资料页直接空白。说明当前角色名/性别不是这些简单字段，可能是**启动时从 flash/名字记录缓存**的。

下一步是反汇编 `0x20146CE0` 的绘制函数和它的调用者，找名字/角色 ID 的真实来源；或者改 flash 记录后强制冷启动。

### 雌性养成与红外求婚：已成功

雌性 `ぷちもちっち` 用同样的 6 小时补时 + 照顾循环养大：

- 婴儿 `ぷちもちっち` → `おだんごなのっち`（0 才）→ `めっとっち`（1 才）→ `わたわたっち`（1 才）→ 3 才成年；
- 3 才时 `ツーしん` 子菜单变成 `あそぶ アイテムこうかん プロポーズ おでかけ`，与雄性 `ござるっち` 一致。

两个关键点：

1. **玩耍要走完整的 `たからばこ → おどうぐ → ボール → つかう`**。只按到 `たからばこ` 不会加 `あいじょー`；完整玩一次约加 1 格，约 40～45 次可以把 `あいじょー` 条填满。工具 `irplay <save> <hour> <count>` 会重复这套动作。
2. **成长计时与年龄显示分开**。2026-11-12 的原固件分析确认：正常进化按累计成长分钟触发，没有午夜条件；状态页年龄的常规日更在 00:00 按累计分钟重算。旧实验把现象归因为“必须醒着跨午夜”并不充分，现已更正。暂停跨日可能跳过年龄刷新，详见[年龄、进化与暂停跨日研究](sweets-age-and-pause.md)。

双机求婚流程（`irmarry`）：

```
A（雄性）: ツーしん → みーつ → プロポーズ
B（雌性）: ツーしん → みーつ → あそぶ
两边都在等待画面按 B → つうしん ちゅう
```

实测屏幕顺序：

```
B: ぼくとけっこんして ほしいでござる
B: けっこん する しない
   （在 B 上按 B，选「する」）
B: うれしい！いっしょにしあわせになりたいわた
B: おめでとう！
```

结果：

- 交换了 171,310 字节的红外帧（含 `TMGC` OBEX 数据）；
- B 回到房间后手里抱着一颗蛋，婚姻成立；
- 稳定存档：`/tmp/female-married`、`/tmp/male-married`；
- 截图：`/tmp/marriage-happy.png`（两人同框）、`/tmp/marriage-congrats.png`（おめでとう！）、`/tmp/marriage-egg.png`（雌性抱蛋）。

**时序要点**：两台设备的第二次 B 必须错开。两边同时开始时会在 `つうしん ちゅう` 之后直接 `つうしん しっぱい`（断开的爱心）；先让 A 开始 0.5 秒，再让 B 开始，才能完成交换。这个 `lead` 是 `irmarry` 的第 7 个参数。

## 二维码配对原型（本地）

用 `irlanqr` 验证“展示二维码的一方就是 Host，扫码的一方自动连接”。

```sh
# Host：二维码写到 /tmp/tama-join.png
POCKET_MEETS_ROM=... irlanqr host /tmp/a 0 35 10 0

# 扫码：从同一张 PNG 解出 payload，再直接连接
PAYLOAD=$(node tools/qr/qrscan.cjs /tmp/tama-join.png)
POCKET_MEETS_ROM=... irlanqr join "$PAYLOAD" /tmp/b 35 10 0
```

二维码内容：

```
tama://join?v=1&h=127.0.0.1,192.168.2.123&p=53027&t=<token>&c=371189
```

- `h`：候选地址，Host 本机 + 局域网地址；
- `p`：TCP 端口；
- `t`：一次性 token；
- `c`：6 位兜底码；
- Join 按顺序尝试每个地址，单个地址 2 秒超时。

实测：

```
Host: QR /tmp/tama-join.png
Join: CONNECTED 127.0.0.1:53027
Host: done sent=66717 recv=53686
Join: done sent=53686 recv=66717
Host: バイバイ★またいっしょに あそびたいでござる
```

二维码生成/解码的 Node 依赖只用于本地原型；iOS 端用 CoreImage
`CIFilter.qrCodeGenerator` 和 VisionKit / AVFoundation，不需要 Node。

`IRLAN_NATIVE=1` 是原生按键模式的实验开关：连接后不自动导航，由 stdin 的
`a/b/c` 驱动。当前两个存档的起始界面可能不同（一个在房间、一个还停在
`ツーしん`），脚本化按键不一定对齐；正式 App 里由用户看屏幕操作，不存在
这个问题。默认（不带该变量）是已经验证过的自动会话。


### 本地二维码演示包


脚本会：

## 局域网（TCP）调试

本地已经用 **纯 TCP** 跑通两台模拟器，不经过 HTTP 请求/响应。一个进程做
host，一个进程做 join，两边各自跑原版固件，只把 UART 字节通过 socket 转发。

```sh
# 终端 1
POCKET_MEETS_ROM=... irlan host /tmp/lan-a 47000 35 10 0

# 终端 2
POCKET_MEETS_ROM=... irlan join /tmp/lan-b 47000 35 10 0
```

参数：`<role> <save> <port> <seconds> <hour> [option]`，`option` 0 是
`あそぶ`，2 是 `プロポーズ`（host 主动，join 等待并自动回答 `する`）。

### 关键实现

1. **控制握手**：连接后先交换 `TAMA-LAN 1`，然后双方各自导航到
   `みーつ` 子菜单；到 `つうしん たいき…` 后交换 `WAIT`，host 发 `GO`。
2. **tick barrier**：每 20 ms 一步，双方各发一个 `tick` 帧，收到对方的
   `tick` 才进入下一步。这样两个独立进程的模拟时间保持锁步；否则一边跑
   得快、一边跑得慢，IR 固件会超时。
3. **仿真时间 lead**：host 在第二次 B 之后多 `step(0.5)`；join 不额外
   step。注意这必须是**仿真时间**，不能只用 wall-clock sleep。最早版本
   只错开墙钟，结果 315 字节后一直重发；改成仿真时间 0.5 s 后立刻变成
   正常的 120 KB 访问。
4. **帧格式**：`[type: u8][len: u16 LE][payload]`；`type 0` 是 UART 字节，
   `type 1` 是 tick。TCP 保证顺序，不需要给每个字节编号。

### 实测

| 流程 | A→B | B→A | 结果 |
|---|---|---|---|
| `あそぶ` | 66,717 | 53,686 | 完成访问，join 端 `おでかけ ちゅう` |
| `プロポーズ` | 85,167 | 86,000 | join 端 `おめでとう！`，host `おでかけ ちゅう` |

这两组字节数和本地同进程桥接完全一致（本地 `あそぶ` 同样是
66,717 / 53,686），说明 TCP 传输没有改变固件看到的数据。

### iOS 落地建议

- 用 `Network.framework` 的 `NWListener` / `NWConnection` 跑 TCP，不要用
  `URLSession` 的 HTTP 请求；二维码可以不做，host 显示 IP:端口即可。
- 两端都前台时最稳；后台会挂起 socket。
- 先保留这个 `irlan` 作为桌面回归测试：每次改传输层，都能和本地同进程
  桥接的字节数对比。
- 以后要离线，再把 `MultipeerConnectivity` 或 BLE 接到同一个“字节流 +
  tick barrier”接口下面。
