# Sweets v062：成长分钟与进化机制

本记录只覆盖成长计数和进化触发。状态页年龄、午夜刷新及 App 暂停恢复由同轮研究的主报告说明。

目标是用户的 `fw_tg18_jp_v062_2019-09-12_sweets.bin`，SHA-256：
`1b0972205bc104183e2406510f264d7ed4193bb5dc08c4811447ab986bbd2305`。
以下使用 Capstone 5.0.6 反汇编和现有 `tg18-core` 执行原固件取得证据；不是 REA 工具的 Evidence 输出。
不外推到其它 Meets / On 固件。所有执行均使用仓库外的存档副本，未修改实机、原始 ROM 或源存档。

## 两个不同的字段

参数区基址为 `0xF800D834`。

| 字段 | 地址 | 类型 | 用途 |
| --- | --- | --- | --- |
| `+0x1C` | `0xF800D850` | little-endian u32 | 本文确认的累计成长分钟 G |
| `+0x36` | `0xF800D86A` | little-endian u16 | 状态页年龄，不等于成长分钟计数器 |
| `+0x52` | `0xF800D886` | u8 | 阶段：1 婴儿、2 儿童、3 少年、4 成人 |
| `+0x3FF` | `0xF800DC33` | u8 | 正常主循环中的秒计数，每 60 次触发分钟处理 |

阶段映射也由 ROM 字符表确认：`0x201C2914`、每项 `0xE4` 字节，记录的 `+7` 字节为阶段，
婴儿记录为 1、儿童为 2、少年为 3、成人记录为 4。选择角色后在 `0x20155B48`、`0x20155CC8` 写入参数阶段。

## 静态：分钟处理与进化阈值

分钟处理函数是 Thumb `0x201546E8`。正常循环 `0x201E9EC4` 中：

1. `0x201EA296..0x201EA29A` 将 `+0x3FF` 加一；
2. `0x201EA2B6` 检查它是否大于 59；
3. `0x201EA3A6..0x201EA3AC` 清零；
4. `0x201EA3AE..0x201EA3B0` 调用 `0x201546E8`。

快照还包含该主循环的 SRAM 副本。相应实际入口是 `0xF8005582..0xF8005584`，
使用常量 `0xF8005770 = 0x201546E9`（带 Thumb 标记的地址）。

分钟函数满足下节门控时，在 `0x20154758..0x2015475C` 将 G 加一。它用累计 G 触发：

| 当前阶段 | G 到达 | 指令地址 | 行为 |
| --- | ---: | --- | --- |
| 1 婴儿 | 60 分钟 | `0x201547E2..0x201547E8` | 请求进化事件 `0x80` |
| 2 儿童 | 1500 分钟，即累计 25 小时 | `0x20154808..0x20154816` | 请求进化事件 `0x80` |
| 3 少年 | 2940 分钟，即累计 49 小时 | `0x2015481E..0x2015482C` | 请求进化事件 `0x80` |

因此从阈值看，正常阶段依次需要累计 1 小时、再 24 小时、再 24 小时的有效成长计数。
这不是现实墙钟保证；门控、暂停和是否执行分钟处理会影响计数。
阶段 1 的 G=10、45 还有其它照顾逻辑，不能把它们当成进化阈值。

`0x20153708(0x80)` 在参数 `+0x0C` 中设置事件位 `0x80`，相关指令为 `0x201537DC..0x20153804`。
已有该事件时，分钟函数把用于阈值判断的有效阶段加一（`0x2015475E..0x2015476A`），
避免同一阶段反复触发。事件分发在 `0x20145D90` 清事件，随后 `0x20145D9C..0x20145D9E`
调用 `0x20156A9C`，由后者分派进化动画和角色选择。

**这些进化阈值直接比较累计分钟，没有比较午夜。** 这与“年龄显示何时刷新”是两个问题。

## 静态：门控和计数重写边界

G 自增前有以下提前返回条件：

- `0x2014EBC0()` 返回非零；
- `0x2014D340()` 返回非零；此版本该函数实际是返回 0 的 stub；
- `0xF800BEF0 + 0x14` 非零；
- `0xF800DC34 + 0x19` 非零，即 `0xF800DC4D`。

即使经过这些门控，`参数 +0x16 & 4` 为真仍不增加 G（`0x20154750..0x20154756`）。
这个位与异常照顾状态有关：`0x2015430C` 增加参数 `+0x15`，第五次会设置 `+0x16` 的 bits `1|4`
（`0x2015434C..0x20154356`）。本轮没有取得原字段名称，因此不把它叫作“睡眠位”。

正常的阶段阈值使用同一个累计 G，而不是进化后从零计时。所见正常事件分支没有清 G。
但**不能概括为“只有出生会重置 G”**：有限静态扫描已找到这些写入：

- `0x20156642` 清零；
- `0x2015698E` 写 1；
- `0x20147656` 清零；
- `0x2015CA30` 按阶段重建基数：stage 1→1、2→60、3→1500、4/5→4380。

最后一个 helper 的直接调用点包括 `0x2015CD92`、`0x2015E088`、`0x2015E4D0`，
之后还会立即重算年龄字段。尚未完整追这些特殊入口的 UI 语义；不能把本轮扫描当作全部间接写入的穷尽证明。

## 静态：时间与睡眠的解释限制

内部月、日、时、分分别位于参数 `+0x8D/+0x8E/+0x8F/+0x90`。
**`+0x79` 是秒，不是睡眠标记**：

- `0x20158920` 取得 RTC 时间，并在 `0x20158966` 将秒写入 `+0x79`；
- 设置内部月日时分的函数 `0x20158878` 在 `0x20158896` 把这个秒字段清零。

主循环另有逐分钟补时路径：`0x201E9FCE..0x201EA02C` 对内部分钟、小时、日和月进位，
每次迭代经 `0x201E9F9A..0x201E9F9C` 调用同一成长分钟函数。
这与只覆盖 RTC/日内时间字段不同，后者不自动证明这条补时路径已执行。

成长分钟函数没有直接的睡眠字段判断，**但不能据此断言睡眠计入或不计入成长**。
CPU 深睡时是否唤醒、何时运行分钟处理、醒来是否补时，都需要结合实际运行路径验证。
仅见某个夜间快照 G 不动，不足以证明次晨也不会补计。

## 受控执行：直接调用 ROM 分钟函数

私有工具载入真实 `room.t18s`，通过明确的 RAM fixture 清除无关 UI 门控，直接执行 `0x201546E8`。
它验证的是这些分支的行为，不代表自然养育过程：

| 准备条件 | 执行结果 |
| --- | --- |
| stage 4、G=4513、flags=0 | G=4514 |
| 相同条件、`+0x16=4` | G 仍为 4513 |
| 相同条件、秒字段 `+0x79=1` | G=4514 |
| stage 1、G=59 | G=60，事件位 `0x80` |
| stage 2、G=1499 | G=1500，事件位 `0x80` |
| stage 3、G=2939 | G=2940，事件位 `0x80` |

所有直接调用都成功返回。

## 自然短回放：没有改成长参数

另取新的 `room.t18s` 副本，经 `Session::open_care` 加载；turbo=1，保持显示唤醒，RTC/TOD 定位到 10:00，
不直接调用 ROM 函数，不修改成长参数，用正常 `Session::step(0.02)` 跑 180 模拟秒。

| 模拟经过秒数 | G | `+0x3FF` 秒计数 |
| ---: | ---: | ---: |
| 0 | 4513 | 2 |
| 30 | 4513 | 32 |
| 60 | 4514 | 2 |
| 90 | 4514 | 32 |
| 120 | 4515 | 2 |
| 150 | 4515 | 32 |
| 180 | 4516 | 2 |

这确认该清醒基线中，每 60 模拟秒积累一个成长分钟；没有拿受控函数调用冒充自然计时结果。
它不覆盖完整夜间睡眠或多次暂停的情况。
