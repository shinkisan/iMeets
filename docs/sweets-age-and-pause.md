# Sweets v062：年龄、进化与暂停跨日

2026-11-12，针对用户的 `fw_tg18_jp_v062_2019-09-12_sweets.bin` 做本地固件分析和存档副本回放。
ROM SHA-256：`1b0972205bc104183e2406510f264d7ed4193bb5dc08c4811447ab986bbd2305`。
代码指纹：`tg18::code_hash = 0x28ad63c34fa9e369`。
使用 Capstone 5.0.6、现有 tg18-core 和 Session；不是 REA 引擎的 Evidence 输出。
未修改实机、原始 ROM 或输入存档。逆向研究阶段没有更改 App 行为；后续年龄缓存补刷修复见本文末尾。

## 结论

1. **正常进化不要求完整过夜，也没有午夜条件。** 固件根据累计成长分钟请求进化事件。
2. **状态页“几才”是独立字段，不是每 24 小时自动变化的实时显示。** 常规日更在内部时分为 `00:00` 时，把它更新为 `ceil(成长分钟 / 1440)`。
3. **频繁暂停不由 App 主动清零成长分钟。** 暂停的 pump 不运行 CPU；恢复却会对齐手机 RTC/TOD，制造“模拟运行时间没走、钟表跳到另一天”的情形。
4. **跨日恢复可能跳过常规年龄刷新。** 同一副本从 23:59 跳到翌日 10:00 后，短回放中年龄保持旧值；自然跨到 00:00 或直接跳到 00:00 都刷新了。
5. 不能再把旧笔记的“午夜时宠物必须醒着才加龄”当作通用规则。成长、年龄缓存刷新、CPU 深睡及醒来补时是不同路径。

## 证据定位

以下地址是反汇编和模拟器内存追踪所见地址；名称为本轮分析标签，不是厂商源码名称。

| 内容 | 地址 / 指令 | 证据 |
| --- | --- | --- |
| 参数区 | `0xF800D834` | 原固件读写及运行快照 |
| 累计成长分钟 G | `+0x1C = 0xF800D850`，u32 LE | 分钟函数自增，正常 180 秒回放增加 3 |
| 显示年龄 A | `+0x36 = 0xF800D86A`，u16 LE | 状态页 `0x2015F8F4` 读取；画面显示 `3才` 时字段为 3 |
| 阶段 | `+0x52 = 0xF800D886` | 1 婴儿、2 儿童、3 少年、4 成人 |
| 进化分钟处理 | `0x201546E8` | 正常每 60 模拟秒调用，满足门控后 G 加一 |
| 常规日更 | `0x20154438` | 读取内部月日时分；`0x2015454C..52` 判断 hour OR minute 为 0 |
| 年龄计算 | `0x201545FA..0x20154614` | G 加 `0x59F=1439`，除 `0x5A0=1440`，`STRH` 写 A |
| 除法 | ARM `0x201A70DC` | 无符号除法；受控原固件调用验证了边界值 |

关键年龄逻辑可写成：

```text
常规日更入口：
    如果全局门控允许，且内部 hour == 0、minute == 0：
        A = (G + 1439) / 1440     // 无符号整数除法
```

这里没有 `A += 1`，也没有“已睡够一晚”的比较。
同样，状态页不会在每次绘制时重新算 A，而是读取保存的 A。
因此“成长计数继续积累”和“页面数字没有刷新”可以同时发生。

这不是 A 的唯一写入点。还找到初始化清零，以及 `0x2015CDAA`、`0x2015E0A0`、`0x2015E4E8`
等特殊路径：它们先经 `0x2015CA30` 按阶段重建 G，再使用相同公式写年龄。
本轮未完整命名这些入口的 UI 语义，不能说“年龄只能在午夜变化”。

成长阈值及门控详见 [成长分钟报告](age-growth-firmware-notes.md)：
正常累计 G=60、1500、2940 时，分别请求下一阶段的事件 `0x80`；有事件待处理时还会防止重复触发。
阈值不是现实墙钟承诺，异常状态门控、是否执行分钟处理和特殊状态重建会改变实际过程。

## 实验一：直接执行年龄函数，验证公式及时间门控

这是**受控函数实验**：载入真实副本后，人工准备 G、A=77 和内部时分，再直接执行原 ROM `0x20154438`。
不是自然养育，也没有把修改出来的年龄当作自然成长。
所有函数调用均成功返回，结果如下：

| G（人工准备） | 内部时刻 | 执行后 A |
| ---: | --- | ---: |
| 0 | 00:00 | 0 |
| 1 | 00:00 | 1 |
| 60 | 00:00 | 1 |
| 1439 | 00:00 | 1 |
| 1440 | 00:00 | 1 |
| 1441 | 00:00 | 2 |
| 4513 | 00:00 | 4 |
| 4513 | 10:00 | 77，未刷新 |
| 4513 | 00:01 | 77，未刷新 |

原始工具和日志：`../tama-private/age-research/age-functions/`、`age-formula.log`。

## 实验二：不改年龄/成长参数，比较跨午夜与时钟跳变

从同一个 `room.t18s` 起点分支，初始 A=3、G=4513、阶段=4。
在各自全新的输出目录加载副本，turbo=1，先把时钟放到 23:59:50 附近。
通过正常 `Session::step` 跑固件，未直接调用年龄函数，未修改 A 或 G。

| 分支 | 操作 | 短回放结果 |
| --- | --- | --- |
| `cross-awake` | 连续运行经过午夜 | A：3→4，G=4513；追踪到 `0x20154614` 写年龄 |
| `jump-awake` | 覆盖 RTC/TOD 基准，跳到翌日 00:00 | A：3→4，G=4513；同一写入点 |
| `jump-morning` | 覆盖同四个基准，跳到翌日 10:00 | A 仍为 3，G=4513；没有年龄写入 |
| `jump-same-minute` | 跳过整天到 23:59，再连续经过午夜 | 后续自然进入 00:00 时 A=4 |

前两项说明：**不需要完整运行一整晚，短短跨过午夜就能触发年龄缓存刷新。**
第三项说明：把钟表对齐到第二天上午，不等价于实际执行午夜处理。

这些跳时分支模拟的是恢复所写的四个 RTC/TOD 基准字段；不是通过真实 iOS UI 暂停数小时。
`Session::step` 自身不检查 `care.paused`，所以这里刻意不用它来宣称“已模拟暂停”。
正式暂停行为另由源码审计和 `fragmented-pause` 实验检查。

还观察到某些常亮跳时分支中，完整 RTC 已到次日，而固件自己的日期副本仍停在前一天。
静态可见 ARM `0x20007D1C` 读取 SoC 日内时间，只有缓存的上一小时为 23、当前小时为 0 时才增加日计数
（`0x20007D38..0x20007D54`）。直接跳到 10:00 不满足这个条件。
这说明时钟同步也可能留下游戏内部日历滞后；本轮没有穷尽日期重置/冷启动入口，不能推出永久无法恢复。

## 实验三：深睡后跳时的有限观察

`sleep-resume` 分支先解除常亮，实际观察到 CPU `powered_off=true`，再把 RTC/TOD 跳到次日 10:00 并唤醒。
短回放内日期副本到次日，A 仍为 3、G=4513，没有自动补成“年龄 4”。
该回放出现两条模拟器未映射访问提示，且未覆盖整个夜晚，故只保留为有限观察，
不拿它证明所有角色、睡眠时长、晨起流程都一样。

正常固件还存在逐分钟补时循环，也会调用成长分钟函数和日更函数。
所以“夜间某刻 G 没变”不能推出“睡眠永远不计入成长”，
也不能根据常亮实验要求宠物在真正硬件上半夜醒着。

## 实验四：两段 30 秒，中间经过暂停/恢复 API

另开副本，使用正式 `Session::care_pause` 和暂停时的 `Session::pump`，观察原固件成长计数。
暂停 pump 的输入人为给出一天的 `dt`/未来 `now_unix`，用以检查大间隔也不能推进暂停状态；
没有真的等待一天。恢复 API 仍使用真实系统时间，因而 RTC 从存档日期跳到当前日期。
随后用正常 step 运行第二段 30 秒；没有直接调用成长函数或修改 G。

| 阶段 | G | 模拟秒 |
| --- | ---: | ---: |
| 起点 | 4513 | 296231.813 |
| 运行第一段 30 秒 | 4513 | 296261.813 |
| 暂停 pump 收到一天间隔 | 4513 | 296261.813，CPU cycles/game_time 也断言未变 |
| 调用恢复 API，对齐当前 RTC | 4513 | 296261.813 |
| 运行第二段 30 秒 | 4514 | 296291.813 |

这份副本证明不足一分钟的进度跨暂停保留，两段运行会合计成一个成长分钟；
恢复时跳日没有把 G 清零。本实验不是长期 UI 压测，也不涵盖每种睡眠或异常照顾状态。
原始日志为 `../tama-private/age-research/fragmented-pause.log`。

## 对当前暂停设计的含义

源码审计详见 [暂停与时钟报告](age-pause-clock-audit.md)。
当前恢复不会直接修改 A、G 或阶段，也不补跑暂停间隔；它只排除 care 欠账并重新对齐时钟。
因此这两件事都可能成立：

- 分段玩耍的成长进度保留，不要求一次连续玩满 24 小时。
- 每晚暂停、白天恢复，可能长期没有走到常规 00:00 年龄刷新，导致数字滞后。

这不应被描述成“必须过完整的一夜才能成长”，也不应承诺“累积到 24 小时，资料数字当场加一”。
上述实验是修复前的机制验证。后续补刷只处理年龄缓存，不补算暂停成长或执行整套午夜事件。

## 后续修复：build 10022

`rust/shell/src/age.rs` 用 ROM 代码指纹限定已验证的 Sweets v062；正常同日恢复不改年龄。
当暂停恢复时，冻结 RTC 所在的本地日期早于手机日期，会在 `care.json` 持久化
`age_refresh_pending`。原地恢复与打开已暂停存档恢复都走这条检查。

pending 补刷等 CPU 不再深睡，并给 SRAM 重建两秒模拟时间，再检查阶段 1..4、计数和年龄范围。
使用原固件的 ceil(G/1440) 规则，只在目标年龄高于旧值时改 `0xF800D86A` 的两字节缓存。
不改 G、秒计数、阶段或进化事件，不调用午夜日更函数，也不替暂停时间补成长。
当前已打开的资料画面可能保留旧像素，重新进入资料页会读取修正值。

完成补刷会同时保存 Snapshot 与 care 元数据；修正前退出、处于休眠或存档失败时不会丢掉待处理标记。
即使固件在等待期间已自行刷新，也要保存快照后再清 pending，防止重开还原旧缓存。

2026-11-12 本地 83 项测试通过，其中包含带私有 ROM/快照的三项集成验证：

- 当前会话跨日恢复：原 G 保留，A 从 3 补到 4；
- 保存的暂停进度重新打开：pending 跨退出保留，完成后再打开仍为 A=4；
- 确认 `powered_off=true` 的真实快照：冷启动后再补 A，G 保留。

另验证了同日不补刷、倒拨时间不触发、暂停/深睡时不写缓存、未识别固件不支持，以及除两字节 A 外不改准备的 SRAM。
回归命令（私有样本不提交）：

```sh
POCKET_MEETS_AGE_FIXTURES=/path/to/potty-research \
POCKET_MEETS_AGE_SLEEP_SNAPSHOT=/path/to/before-sleep-resume.t18s \
cargo test --release --manifest-path rust/shell/Cargo.toml --lib
```

这项修复不等于解决所有跨日的日历事件；它只补足此处已逆向确认的年龄缓存。
